# Language declaration and responsive images

Two findings from an external SEO audit, and what was changed. Written here
rather than as comments in `index.html`, because comments in that file are copied
into all 71 prerendered pages — a long explanation there is shipped on every
request for no benefit.

## 1. "Invalid country" / invalid language code

**Reported:** language detected `en`, language in HTML `en-in`, language in the
HTTP-Equiv meta tag `en-in, en`, server location Germany → *Invalid country*.

**Cause.** `index.html` carried:

```
<meta http-equiv="content-language" content="en-IN, en" />
```

Three separate things are wrong with it, and all three point the same way:

- The `content-language` pragma is **non-conforming in HTML5**. The spec
  replaced it with the `lang` attribute.
- It was never permitted to carry a comma-separated list. `en-IN, en` is not a
  language code, which is exactly what the validator reported.
- Google ignores it either way, so it was buying nothing.

**Fix.** The pragma was removed. `<html lang="en-IN">` is now the only language
declaration, and it is already correct BCP 47 — `en` plus the `IN` region.

**Do not** add the pragma back, and **do not** "simplify" the `lang` attribute to
plain `en`: the regional variant is accurate for this site's audience (India,
Nepal, Bangladesh, Pakistan, Sri Lanka).

### The "server location: Germany" line was not fixed

That is the audit observing that the Hostinger server answering the request sits
in Germany while the business and its audience are in India. It is **not** an
HTML defect and nothing in this repo can change it — it is a hosting-region
choice. It has a small, real effect on TTFB for Indian visitors.

Two honest options, neither taken here because both are decisions, not fixes:

- Move the site to a Hostinger datacentre in India (support request; involves
  downtime).
- Put a CDN in front, which terminates connections near the visitor. This is
  already planned for a different reason — see
  `docs/cloudflare-dns-migration.md`.

## 2. Responsive image test failed

**Reported:** "This webpage is serving images that are larger than needed for the
size of the user's viewport."

It was right, and one of the problems was worse than reported.

### What was wrong

| Image | Served | Actually drawn | Waste |
|---|---|---|---|
| `consultant-office.jpg` | **1024×1024**, 93 KB, one size for every viewport | 588px wide desktop, ~343px mobile, cropped to 3:2 | ~10× the pixels on a phone |
| Brand logo | `android-chrome-192x192.png`, 18 KB | 24×24 header, 32×32 footer, 26px admin, 28px dashboard | 8× linear, 64× the pixels |
| Unsplash hero on `/study-visa` | `?w=1200`, one size | ~592px desktop, 100vw mobile | ~2× on desktop, ~3× on mobile |

Two details the audit could not see:

1. **The declared dimensions were wrong.** The markup said
   `width={800} height={533}` for an image whose real intrinsic size is
   1024×1024. The element therefore described a 3:2 box around a square file and
   relied on `object-cover` to crop it.
2. **A WebP already existed and was never used.** `consultant-office.webp`
   (50 KB vs 93 KB) had been generated by `npm run images` but the markup pointed
   at the JPEG.

### What changed

`scripts/optimize-images.mjs` now generates responsive variants, so they are
reproducible with `npm run images` rather than being one-off files:

- `consultant-office-{400,800,1024}.{webp,jpg}` — **pre-cropped to 3:2**, which
  is what `object-cover` was cropping to anyway. Shipping the crop instead of
  performing it means the declared intrinsic dimensions now describe the real
  file, and no downloaded pixels are discarded.
- `favicon/logo-{48,96}.png` — generated from the 512px master, 2 KB and 3 KB.

Widths come from the measured layout, not a generic ladder. `why-us.tsx` draws
the photo inside `max-w-7xl` (1280) less 48px padding, in a 12-column grid with a
56px gap, spanning 6 → **588px desktop, 100vw below `lg`**. That is what the
`sizes` attribute says. No 1600px variant is generated because the source is only
1024 wide and upscaling adds bytes without detail.

The `/study-visa` hero needed no new files: Unsplash resizes on its own CDN via
the `w` parameter, and `auto=format` already in the URL makes it serve WebP or
AVIF to browsers that accept it — which is why that one has a `srcset` but no
`<picture>`.

### Measured result

Verified in a real browser against `vite preview`, not from DevTools inspection
alone:

| Case | Before | After |
|---|---|---|
| Photo, 375px viewport @ DPR 2 | 93 KB JPEG | **23 KB** `consultant-office-800.webp` |
| Photo, 658px viewport @ DPR 1.25 | 93 KB JPEG | 32 KB `consultant-office-1024.webp` |
| Logo, 24×24 @ DPR 2 | 18 KB (192px) | **2 KB** `logo-48.png` |
| `/study-visa` hero, 375px @ DPR 2 | `w=1200` | `w=800` |
| Aspect ratio vs declared | 1.000 vs 1.501 (mismatch) | 1.499 vs 1.501 |

### Still outstanding

**Blog and urgent-requirement images are not responsive.** Those come from
Supabase Storage as a single uploaded file (`featured_image`,
`detail_image_url`), so there are no variants to offer and no `sizes` that would
help. Fixing it needs one of:

- Supabase image transformations (a Pro-plan feature) to serve `?width=` variants;
- a transform step on upload in the admin panel, writing several widths; or
- the Cloudflare Worker rewriting those URLs through Cloudflare Images.

Not attempted here — each is a separate decision with a cost attached.

The 3D globe textures in `public/earth-*.{jpg,png}` are **not** `<img>` elements;
they are WebGL textures loaded by three.js and are already resized and converted
by `npm run images`. A responsive-image audit does not see them.
